# Password recovery setup

Password recovery is implemented but disabled until explicitly configured. The sign-in screen will not offer a reset until the application is enabled with a Resend API key and sender address. Email confirmation remains disabled for the development environment.

Before enabling recovery, verify a sending domain in Resend, confirm its sending limits, ensure click tracking is disabled for that domain, and verify actual delivery to a controlled mailbox. Resend configures click tracking per domain, and when enabled it rewrites links through tracking redirects. Do not put member data or real reset links in logs or tickets.

After those prerequisites are satisfied, store the Resend key as the Cloudflare Worker secret `RESEND_API_KEY` using `wrangler secret put`, set `PASSWORD_RESET_FROM` to a sender on the verified domain, and set `PASSWORD_RESET_ENABLED` to `true` in the Worker configuration. Regenerate Worker types, build and deploy. The configured `BETTER_AUTH_URL` must be the app's trusted origin. Leave the feature disabled if any prerequisite is missing. Never commit the key or put it in logs. The sender uses the [Resend email API](https://resend.com/docs/api-reference/emails/send-email).

The reset request returns the same message for known and unknown accounts. The reset link uses a URL fragment so the token is not sent as part of the page request. The form removes the fragment from browser history, and dynamic responses are private and not cached. Better Auth controls expiry (30 minutes), single use and session revocation; the new password must have 12–128 characters. Sending errors are logged generically without the address, link, token or provider error. The message asks the user to contact an administrator if the link does not arrive.

Automated tests use Node SQLite and a simulated Resend HTTP response. An earlier isolated local Worker check used a disposable Cloudflare D1 database and simulated email delivery: it verified neutral responses for known and unknown accounts, password length, session revocation, replay rejection, expired-token rejection and exactly one successful concurrent use. No email was sent externally. Better Auth's rate limiter also returned HTTP 429 during repeated test requests; separate scenarios cleared only the disposable database's rate-limit rows.

Before real-member use, verify the complete flow with a controlled real mailbox, including provider failure, disabled-feature behavior and delivery. Email recovery does not enable or replace the separate email-verification step required before real-member onboarding. On D1, Better Auth executes token consumption, session revocation and password update without a database transaction; if a later step fails the token may be spent, so the member may need to request a new link.
